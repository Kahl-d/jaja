# Lanes

A lane is a long-lived Claude Code session of one type, with a charter, a roster of the agents it may call, and a
scope of files it may write. Lanes exist so several kinds of work can run side by side without stepping on each
other. You do not need them to use the project: every step a lane runs is also a skill or a script you can run by hand
in any session.

Read [CONCEPTS.md](../CONCEPTS.md#lanes-and-the-hub) first if the words "lane" and "hub" are new.

## The eight lanes

| Lane | Does | Roster (agents it may call) |
|---|---|---|
| `recruiter` | The head. Runs the day: sweep, cards, priorities, day queue, reviews, rulings, evening wrap | role-analyst, fit-scorer, tracker-ops, corpus-keeper, legal-visa, messenger, prospector, job-scout, company-researcher |
| `hunt` | Fresh roles and the people hiring for them | job-scout, platform-scout, prospector, company-researcher, fit-scorer, legal-visa, messenger |
| `research` | Understands one role at a time (the role package) | role-analyst, company-researcher, prospector, fit-scorer, legal-visa |
| `resume` | Builds the page for one role from the base and gates it | resume-tailor, resume-editor, base-comparer, hiring-manager-persona, technical-ai-reviewer, technical-recruiter-reviewer, ai-screener, corpus-keeper, role-analyst, company-researcher, prospector, fit-scorer, legal-visa |
| `focused` | The best-chance people and roles, one at a time, at full depth | role-analyst, company-researcher, prospector, messenger, resume-tailor, resume-editor, base-comparer, technical-recruiter-reviewer, technical-ai-reviewer, hiring-manager-persona, legal-visa, tracker-ops, apply-assist |
| `apply` | Mass applications: fills forms from packs, submits only rows your batch yes names | apply-assist, tracker-ops, messenger, legal-visa |
| `posts` | Reads hiring posts on LinkedIn and X, drafts comments and notes, acts only on your yes | prospector, messenger |
| `prep` | Interview preparation: packs, mocks, debriefs | prep-coach |

The recruiter is the one you talk to by default. Open another lane only when you want to work on that part
yourself. The roster, skills, scope, gates and stops of each lane are in `lanes/<type>/LANE.yaml`; its persona and
procedure are in `lanes/<type>/AGENT.md`.

## Launch a lane

Start the lane in your data folder, the folder that holds `hub/`, `applications/` and the rest:

```bash
cd ~/jaja-data
claude --agent lane-recruiter \
  --settings ~/jaja/.claude/lane-settings/recruiter.json \
  --name AG-RECRUITER
```

The pattern is `claude --agent lane-<type> --settings <repo>/.claude/lane-settings/<type>.json --name AG-<TYPE>`, with
`<type>` one of `apply`, `focused`, `hunt`, `posts`, `prep`, `recruiter`, `research`, `resume`. With the plugin
installed, the agent is also available as `jaja:lane-<type>`.

What the settings file does: `.claude/lane-settings/<type>.json` (generated by `sync.py`; do not edit) names the
agent and sets `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` to `1`, so a lane can call its roster but those agents cannot
spawn more.

You can start as many sessions of a type as the day needs; each registers itself.

### What happens at start

Three SessionStart hooks run before the first turn:

1. `lane_context.py` tells the session it is in a programme, what its role is, and what hub events happened since its
   state file was last refreshed.
2. `lane_register.py` writes the session's address, name, branch and role into `hub/registry.json`.
3. `lane_rules.py` prints your standing rulings that apply to this lane type.

Then the lane's `initial_prompt` runs. For the recruiter it reads the charter, finds its address, reads its state
file `hub/lanes/RECRUITER-STATE.md`, appends an identity section to `hub/lanes/RECRUITER.md`, runs the status scripts,
runs the morning sweep and presents the day's cards.

### Two things to check before the first launch

The lane cards were written against a fuller data folder than the blank skeleton gives you. Before you start a lane
for the first time:

- The cards tell the lane to read `AGENCY-CHARTER.md` at the root of the data folder, and to create a lane file from
  `hub/lanes/_TEMPLATE.md`. `init-data.py` does not copy either. Copy `docs/AGENCY-CHARTER.md` to
  `<data>/AGENCY-CHARTER.md` and `templates/orchestration/hub/lanes/_TEMPLATE.md` to `<data>/hub/lanes/_TEMPLATE.md`.
- The resume lane's roster names `ai-screener`, which has no role card yet (see the [roadmap](../ROADMAP.md)). The
  lane works without it; its other readers run.

## The hub folder

The hub is `<data>/hub/`. Its files:

| File | What it is | Written by |
|---|---|---|
| `programme.json` | The pointer the lane hooks read: programme name, prefix, branch, hub path | `init-data.py`, `new-programme.sh` |
| `registry.json` | Every live session's address, name, branch, role | `lane_register.py` at session start |
| `rulings.yaml` | Your decisions, each in your own words with a unique id | `scripts/rulings.py add` |
| `events.jsonl` | One JSON line per ruling, park, go or order change | `scripts/kernel/hub_events.py` |
| `lanes/<TYPE>.md` | A lane's append-only log: identity, posts, handoffs | that lane only |
| `lanes/<TYPE>-STATE.md` | The lane's small live state, so a restart reads a few kilobytes | `lane_handover.py`, `scripts/kernel/lane_state.py` |
| `briefs/` | Briefs for a lane | the orchestrator |

The write rule is one author per file, enforced by `lane_write_guard.py`: a lane writes its own file, not another
lane's; only the orchestrator writes `ORCHESTRATOR.md`, `SIGNAL.md`, briefs and the like. When a lane's turn ends
having changed files, `lane_handover.py` writes the handoff section (the files and their sha256) for it.

### Working through the day queue

The recruiter builds a ranked queue; the other lanes claim from it:

```bash
python3 scripts/day_queue.py show
python3 scripts/day_queue.py claim --lane <address> --kind resume
```

`show` takes `--kind` (research, resume, apply, focused, posts, portal, mass, prep, hunt), `--status` (open, claimed,
done, blocked) and `--channel`. Subcommands are `build`, `claim`, `done`, `release`, `add` and `show`.

### Recording a ruling

When you decide something that should bind later sessions ("never contact this person", "applications are paused"),
record it once:

```bash
python3 scripts/rulings.py next          # the next free id
python3 scripts/rulings.py add --help    # --quote (your exact words), --source, --topic, --reading, --scope-lanes ...
python3 scripts/rulings.py check
```

The hooks then print the ruling to every lane and role it names. Nothing else copies it; cards and briefs link its
id.

### A separate programme

`scripts/kernel/new-programme.sh --programme "<name>" --root <dir>` scaffolds a hub (and its tracker and division
files) from `templates/orchestration/` for a different multi-session effort. It refuses to overwrite an existing hub
unless you pass `--force`; do not scaffold a second hub beside a live one.

## Browser lanes: one keyboard per browser

Lanes that drive a logged-in Chrome (recruiter, hunt, focused, apply, posts) share the problem that keystrokes go to the
window's active tab. `browser_lease.py` enforces a focus rule: a session must bring its own tab forward before its
first click or type, and again after another session touched Chrome. Give each browser lane its own Chrome window or
profile.

## Stopping

A lane stops at the end of its turn like any session. The Stop hooks write the handoff and release the browser
lease. Pausing everything is a ruling and a note in the hub, not a kill command; routines are off by default, so
nothing else is running.
