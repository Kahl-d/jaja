# Customizing agents and skills

Agents, skills, lanes and routines are all Markdown or YAML files. You change them by editing the source file and
rendering. This guide covers the cards, the workshop skills that scaffold new ones, and the checks that keep the
result consistent.

## The rule: edit sources, then sync

| Edit this (source) | Never edit this (generated) |
|---|---|
| `agents/<name>.md` | `.claude/agents/<name>.md`, `.codex/agents/<name>.toml` |
| `lanes/<type>/AGENT.md`, `lanes/<type>/LANE.yaml` | `.claude/agents/lane-<type>.md`, `.claude/lane-settings/<type>.json` |
| `skills/<name>/SKILL.md` | `.agents/skills/<name>/` |
| `hooks/hooks.json`, `.mcp.json` | `.claude/settings.json` (hooks key), `.codex/hooks.json`, `.codex/config.toml` |

Every generated file carries a `GENERATED by scripts/kernel/sync.py` marker, and the `guard_generated_files.py` hook
refuses edits to a marked file. After any change:

```bash
python3 scripts/kernel/sync.py          # render
python3 scripts/kernel/sync.py --check  # exits 1 on drift, writes nothing
python3 scripts/kernel/lint.py          # schemas, links, skill descriptions, budgets, adapters
python3 scripts/doctor.py               # the whole health check
```

The skills `/jaja:sync` and `/jaja:doctor` run the same commands from a session.

## Role cards

A role card is `agents/<name>.md`: YAML frontmatter, then a body. The frontmatter is the contract. Copy
`templates/role-card.md` and fill every key.

| Key | Meaning |
|---|---|
| `name`, `title`, `purpose` | Identity. `purpose` becomes the native `description` in the generated file |
| `tools_allow` | The tools the role may use. Never empty: Claude Code reads an empty list as "all tools", so `sync.py` refuses such a card and `lint.py` reports `role-tools-empty` |
| `tier_max` | `T0` to `T3`: the highest tier the role may act at (see [CONCEPTS.md](../CONCEPTS.md#tiers-t0-to-t4)) |
| `deny_commands` | Shell patterns the role may never run, enforced by the `role_deny.py` hook. Example from the messenger: `gmail_send.py execute` |
| `disallowed_tools` | Tools the role may never call |
| `connectors` | Names of connectors the role uses, for the connector map |
| `model`, `effort`, `max_turns` | The model and effort for the kind of work. Across the 30 cards: 15 opus, 13 sonnet, 2 haiku |
| `budget` | `{tokens_per_day, runs_per_day}` |
| `skills` | Skills the role uses |
| `reports_to` | Who reviews its work |
| `kpis`, `stop_conditions` | What good looks like, and when the role must stop and ask |
| `status` | `probation`, `active`, `stale` or `archived` |
| `inputs`, `outputs` | Files the role reads and writes (documentation; the lane `scope` and hooks do the enforcing) |

Body sections by convention: Charter, Inputs, Outputs, How I work, Boundaries, Stop conditions, KPIs. Keep it short;
long cards cost context on every spawn (`card_audit.py` flags bloat).

Principles worth keeping when you edit a card:

- **Least privilege.** Give the role the smallest tool list that does its job, and the lowest tier. A reader of
  untrusted content (postings, inbound mail) should not also be able to send.
- **Name the stop conditions.** A role that knows when to stop does less damage than one that is told to be careful.
- **Do not grant send.** Only the `sender` role has send scopes. A drafting role gets `deny_commands` for every send
  path.

## Skills

A skill is `skills/<name>/SKILL.md`: frontmatter with `name`, a `description` of at most 300 characters that says
only when to use it, optionally `disable-model-invocation: true`, and a body of numbered steps that name real files and
commands, ending in a verification step. Of the 52 shipped skills, 27 are hand-invoked only; the hand-invoked set
includes the workshop skills, `doctor` and `sync`, and several that touch your records or other people.

Dates in a skill are computed at run time (`!`date +%F``), never written in.

## The workshop skills

Four skills scaffold new parts. Each interviews you first, then writes from a template, then lints. They and the
two checking skills below them are all hand-invoked.

| Skill | Creates | From |
|---|---|---|
| `/jaja:new-role` | A role card, an evals folder, a probation entry | `templates/role-card.md` |
| `/jaja:new-skill` | A skill folder | `templates/skill/SKILL.md` |
| `/jaja:new-routine` | A routine spec, a receipt folder, a budget line, a watchdog entry | `templates/routine.yaml` |
| `/jaja:new-automation` | An event-driven automation | `templates/automation.yaml` |
| `/jaja:doctor`, `/jaja:sync` | Nothing; they check and render | |

Run `/jaja:new-role` with a request, for example "a role that triages recruiter mail", and answer its
questions: which recurring ticket type or distinct tool justifies a role rather than a skill, what breaks if it
disappears, who it reports to, what it must never do. It then fills the card with `status: probation` and
`version: 0.1.0`, creates `evals/<name>/cases.yaml` with at least three cases, runs `sync.py`, runs `lint.py`, and
dry-runs the role on its cases.

## Adding a role by hand

1. Copy `templates/role-card.md` to `agents/<name>.md`; fill the frontmatter. Set `tools_allow` and `tier_max`.
2. Add `deny_commands` for anything the role must not run.
3. `python3 scripts/kernel/sync.py`, then `python3 scripts/kernel/lint.py`.
4. Add the role to a lane's `roster` in `lanes/<type>/LANE.yaml` if a lane should be able to call it, and re-run sync.
5. Write evals. `evals/README.md` and `evals/example-role/cases.yaml.example` show the format; the harness is
   `scripts/kernel/evals.py` (`list`, `prepare`, `run`, `grade`, `report`). Use synthetic fixtures only.

## Changing a lane

Edit `lanes/<type>/LANE.yaml` (roster, skills, `scope`, `gates`, `stops`) or `AGENT.md` (the persona, the
`initial_prompt`, the day), then run sync. The `scope` is the list of paths the lane may write; the hub write guard
enforces the hub part of it.

## Adding a routine

A routine spec in `routines/<name>.yaml` has: `name`, `purpose`, `runs_on`, `engine`, `model`, `effort`, `schedule`
(cron), `action` (for example `skill:scout-jobs`), `inputs`, `outputs`, `connectors`, `tier`, `notify`, `budget`,
`enabled` and `owner`. Always create it with `enabled: false`. Run the action by hand, read the receipt in
`<runtime>/logs/runs/<name>/`, and only then enable it. `python3 scripts/kernel/watchdog.py --no-inbox` shows the
routine as OFF, then OK, LATE or SILENT once it is enabled.

## Changing a gate or a check

Gates and checks are scripts with tests, not prompts. To change one, edit the script, run its tests against the demo
data, and keep personal values out of it: a threshold belongs in `config/defaults.d/` with a neutral default and in
your `<data>/config/` for your value. See [configuration.md](configuration.md). Run the full default suite with
`python3 -m pytest scripts/tests -m "not real_records and not workspace" -q`.

The checklist is in [CONTRIBUTING.md](../../CONTRIBUTING.md): sync, doctor, the test run on the demo data, and
